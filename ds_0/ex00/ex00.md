# Ex00 - Create Postgres DB

Bu egzersizin amaci PostgreSQL calisan bir veritabani ortami hazirlamaktir. Sonraki
egzersizlerde CSV dosyalarindan tablo olusturacagin icin once PostgreSQL server'in
calisir, baglanilabilir ve dogru ayarlarla kurulmus olmasi gerekiyor.

Subject'in ex00 beklentisi sudur:

```text
Turn-in directory: ex00/
Files to turn in: docker-compose.yml or setup.sh or VM-instructions.txt
Allowed functions: All
```

Yani ex00 icin bu uc secenekten birini teslim etmek yeterlidir:

```text
docker-compose.yml
setup.sh
VM-instructions.txt
```

Bu projede en mantikli tercih:

```text
ex00/docker-compose.yml
```

## Sadece docker-compose.yml mi teslim edilecek?

Subject'e gore evet, Docker yolunu seciyorsan ex00 icin asil teslim dosyasi
`docker-compose.yml` olur.

Ama su ayrimi iyi anlamak lazim:

- `docker-compose.yml` degerlendirilecek asil teknik dosyadir.
- `ex00.md` bu repoda ogrenme notu ve aciklama dosyasidir.
- Subject'in "Files to turn in" satirinda `ex00.md` gecmez.

Yani resmi teslim beklentisi acisindan `docker-compose.yml` yeterlidir. Bu dosyadaki
ayarlar sayesinde evaluator PostgreSQL container'ini baslatabilmeli ve subject'in
verdigi komutla veritabanina baglanabilmelidir.

## docker-compose.yml icerigi

Bu ex00 icin hazirlanan dosya:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: piscineds_postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: ayhan
      POSTGRES_PASSWORD: mysecretpassword
      POSTGRES_DB: piscineds
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - piscineds_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ayhan -d piscineds"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s
    networks:
      - piscineds_network

volumes:
  piscineds_data:

networks:
  piscineds_network:
    driver: bridge
```

## Satir satir aciklama

### services

```yaml
services:
```

Docker Compose'da `services`, calistirilacak container'lari tanimladigin ana bolumdur.
Bir proje icinde birden fazla servis olabilir. Ornegin bir web uygulamasinda `backend`,
`frontend`, `database` gibi servisler olabilir.

Bu projede sadece PostgreSQL gerekiyor. Bu yuzden tek servisimiz var:

```yaml
postgres:
```

Bu servis adi Compose icinde kullanilan mantiksal addir. Container'in gercek adi degil,
Compose dosyasindaki servis ismidir.

### image

```yaml
image: postgres:16-alpine
```

`image`, container'in hangi hazir Docker imajindan olusturulacagini soyler.

Burada:

```text
postgres
```

resmi PostgreSQL Docker imajidir.

```text
16-alpine
```

PostgreSQL'in 16 surumunu ve Alpine Linux tabanli daha kucuk imajini kullanir.

Burada `latest` kullanmamak daha iyi pratiktir. Cunku `latest` zamanla degisebilir.
Bugun baska, yarin baska PostgreSQL surumu indirebilir. Subject Docker kullanirsan
Inception'daki standartlara ve iyi pratiklere uygun olmasini soyluyor; sabit bir surum
kullanmak bu yuzden daha temizdir.

### container_name

```yaml
container_name: piscineds_postgres
```

Bu, olusacak container'a net bir isim verir.

Bu zorunlu degildir ama faydalidir. Container'lari listelerken:

```bash
docker ps
```

veya loglara bakarken:

```bash
docker logs piscineds_postgres
```

hangi container'in bu projeye ait oldugu kolay anlasilir.

### restart

```yaml
restart: unless-stopped
```

Bu ayar container beklenmedik sekilde kapanirsa Docker'in onu tekrar baslatmasini
saglar.

`unless-stopped` su anlama gelir:

- Container hata nedeniyle kapanirsa tekrar baslat.
- Bilgisayar yeniden acildiginda Docker calisiyorsa container'i tekrar baslat.
- Ama kullanici container'i bilerek durdurduysa zorla tekrar baslatma.

Bu ayar veritabani servisleri icin kullanislidir.

### environment

```yaml
environment:
  POSTGRES_USER: ayhan
  POSTGRES_PASSWORD: mysecretpassword
  POSTGRES_DB: piscineds
```

`environment`, container icine ortam degiskenleri verir.

PostgreSQL resmi Docker imaji ilk calistiginda bu degiskenleri okuyarak ilk database
kurulumunu yapar.

#### POSTGRES_USER

```yaml
POSTGRES_USER: ayhan
```

Olusturulacak PostgreSQL kullanici adidir.

Subject'e gore bu kullanici adi senin student login'in olmali. Bu dosyada `ayhan`
kullanildi.

Bu deger sayesinde su komut calisir:

```bash
psql -U ayhan -d piscineds -h localhost -W
```

#### POSTGRES_PASSWORD

```yaml
POSTGRES_PASSWORD: mysecretpassword
```

PostgreSQL kullanicisinin sifresidir. Subject sifrenin kesin olarak
`mysecretpassword` olmasini istiyor.

`psql` komutunda `-W` kullandiginda terminal senden sifre ister; burada girmen gereken
deger budur.

#### POSTGRES_DB

```yaml
POSTGRES_DB: piscineds
```

Ilk calistirmada olusturulacak database adidir. Subject database adinin kesin olarak
`piscineds` olmasini istiyor.

Bu deger sayesinde su kisim dogru olur:

```bash
-d piscineds
```

### ports

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

Container icindeki PostgreSQL servisini kendi bilgisayarina acar.

Bu ifadeyi parcalarsak:

```text
127.0.0.1:5432:5432
```

Soldaki kisim host tarafidir:

```text
127.0.0.1:5432
```

Bu, kendi bilgisayarindaki localhost adresinde 5432 portunu ac demektir.

Sag kisim container tarafidir:

```text
5432
```

PostgreSQL container icinde varsayilan olarak 5432 portunda dinler.

Yani bu mapping sunu yapar:

```text
Bilgisayarindaki localhost:5432 -> container icindeki PostgreSQL:5432
```

Subject su komutu istedigi icin bu port acilmalidir:

```bash
psql -U ayhan -d piscineds -h localhost -W
```

Burada `-h localhost` dediginde psql kendi bilgisayarindaki 5432 portuna baglanir.
Docker Compose da bu baglantiyi PostgreSQL container'ina yonlendirir.

Neden sadece `5432:5432` degil de `127.0.0.1:5432:5432`?

`127.0.0.1` kullaninca port sadece kendi bilgisayarindan erisilebilir olur. Ayni agdaki
baska makineler bu porta dogrudan erisemez. Bu daha sinirli ve daha temiz bir ayardir.

### volumes

```yaml
volumes:
  - piscineds_data:/var/lib/postgresql/data
```

Volume, container disinda kalici veri saklamak icin kullanilir.

Container'lar silinip yeniden olusturulabilir. Eger PostgreSQL verisini sadece container
icinde saklarsan container silindiginde database verin de gidebilir.

Bu satir sunu yapar:

```text
piscineds_data volume'u -> container icindeki /var/lib/postgresql/data klasoru
```

PostgreSQL verilerini bu klasorde saklar. Bu yuzden named volume kullanmak database
icin iyi pratiktir.

### healthcheck

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U ayhan -d piscineds"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 10s
```

`healthcheck`, container'in sadece calisip calismadigini degil, PostgreSQL'in gercekten
baglanti kabul etmeye hazir olup olmadigini kontrol eder.

#### test

```yaml
test: ["CMD-SHELL", "pg_isready -U ayhan -d piscineds"]
```

`pg_isready`, PostgreSQL ile gelen kucuk bir kontrol aracidir. Server hazir mi diye
bakar.

Bu test, `ayhan` kullanicisiyle `piscineds` database'inin hazir olup olmadigini kontrol
eder.

#### interval

```yaml
interval: 10s
```

Docker her 10 saniyede bir healthcheck calistirir.

#### timeout

```yaml
timeout: 5s
```

Healthcheck komutu 5 saniye icinde cevap vermezse basarisiz sayilir.

#### retries

```yaml
retries: 5
```

Arka arkaya 5 kez basarisiz olursa container `unhealthy` durumuna dusebilir.

#### start_period

```yaml
start_period: 10s
```

Container ilk acilirken PostgreSQL'in hazirlanmasi icin biraz sure tanir. Bu suredeki
basarisiz kontroller hemen problem sayilmaz.

Healthcheck subject'te zorunlu degil, ama iyi pratiktir. Degerlendirme sirasinda
"container calisiyor ama PostgreSQL henuz hazir degil" karisikligini azaltir.

### networks

```yaml
networks:
  - piscineds_network
```

Bu servis, asagida tanimlanan `piscineds_network` agina baglanir.

Tek servisli bu projede network teknik olarak sart degildir; Docker Compose zaten
varsayilan bir network olusturabilir. Ama ozel network tanimlamak daha duzenli bir
Compose yapisidir ve Inception tarzi iyi pratiklere daha yakindir.

### top-level volumes

```yaml
volumes:
  piscineds_data:
```

Dosyanin en altindaki bu bolum named volume'u tanimlar.

Yukarida servis icinde su volume kullanilmisti:

```yaml
- piscineds_data:/var/lib/postgresql/data
```

Bu volume'un Compose tarafindaki resmi tanimi burada yapilir.

### top-level networks

```yaml
networks:
  piscineds_network:
    driver: bridge
```

Bu bolum Compose projesi icin ozel bir network tanimlar.

`bridge`, Docker'in varsayilan container network tipidir. Container'lar bu bridge agi
uzerinden birbirleriyle haberlesebilir. Bu projede tek container oldugu icin cok kritik
degildir, ama yapinin temiz olmasini saglar.

## Docker Compose komutu bulunamazsa

Eger su hata benzeri bir durum gorursen:

```text

```

bu PostgreSQL ayarinin yanlis oldugu anlamina gelmez. Sadece sistemde Docker Compose
eklentisi kurulu degildir.

Ubuntu'da paket adi kullandigin apt kaynagina gore degisebilir.

Bu bilgisayarda Ubuntu 22.04 depolarinda gorunen paket adi sudur:

```bash
sudo apt install docker-compose-v2
```

Docker'in kendi resmi apt deposu eklenmis sistemlerde ise paket adi genelde su olabilir:

```bash
sudo apt install docker-compose-plugin
```

Bazi eski sistemlerde bunun yerine ayri `docker-compose` komutu kurulu olabilir:

```bash
sudo apt install docker-compose
```

Ama mumkunse Compose v2 tercih edilmelidir. Hangi komutun mevcut oldugunu kontrol etmek
icin:

```bash
docker compose version
docker-compose --version
```

## Port cakismasi olursa

Eger bilgisayarinda zaten PostgreSQL calisiyorsa 5432 portu dolu olabilir. Bu durumda
`docker compose up -d` hata verebilir.

Ama subject'in bekledigi komut `-h localhost` ile varsayilan PostgreSQL portuna
baglanmaktir. `psql` komutunda `-p` bayragi verilmedigi icin varsayilan port 5432
kullanilir.

Bu yuzden ex00 icin en temiz cozum host tarafinda 5432 portunu kullanmaktir. Port

## Ek Sorular ve Detayli Cevaplar

Bu bolum, `docker-compose.yml` dosyasini daha iyi anlamak icin sorulan ek sorulara
cevap verir.

### 1. Soru: Inception projesinde kullanilacak servisler genelde stable olan son surum seklinde isteniyordu. Yani son surumden bir onceki tutarli surum anlamina geliyormus galiba, dogru mu bu? Bu 16-alpine stable olan son surum mu?

Kisa cevap: `postgres:16-alpine` bugunun bilgisine gore stable bir PostgreSQL surumudur,
ama "son stable surum" degildir. "Sondan bir onceki stable major surum" olarak da artik
dogru degildir.

Burada uc kavrami ayirmak lazim:

```text
latest stable major version
penultimate stable major version
supported stable version
```

#### Latest stable major version

Bu, PostgreSQL'in en yeni kararlı ana surumudur.

17 Agustos 2026 itibariyla resmi PostgreSQL sitesinde desteklenen guncel surumler
soyle gorunuyor:

```text
18.6
17.11
16.15
15.19
14.24
```

Bu listeye gore en yeni stable major surum:

```text
PostgreSQL 18
```

Dolayisiyla "latest stable" yorumu yaparsak Compose image'i su olurdu:

```yaml
image: postgres:18-alpine
```

#### Penultimate stable major version

`Penultimate`, "sondan bir onceki" demektir.

Eger en yeni stable major surum PostgreSQL 18 ise, sondan bir onceki stable major surum:

```text
PostgreSQL 17
```

Bu yoruma gore Compose image'i su olurdu:

```yaml
image: postgres:17-alpine
```

#### Supported stable version

PostgreSQL major surumleri cikinca hemen eski olmaz. PostgreSQL resmi versioning
politikasina gore bir major surum ilk cikisindan sonra yaklasik 5 yil desteklenir.

Bu yuzden PostgreSQL 16 hala desteklenen stable bir surumdur. Ama bu, onun "en son
stable" oldugu anlamina gelmez. Daha dogru ifade:

```text
PostgreSQL 16 stable ve desteklenen bir surumdur, fakat latest stable degildir.
```

#### Bu projede ne secmek daha mantikli?

Subject ex00'da spesifik PostgreSQL surumu belirtmiyor. Sadece Docker kullanirsan
Inception'daki standartlara ve iyi pratiklere uygun olmasini soyluyor.

Bu nedenle kotu secim sunlardir:

```yaml
image: postgres:latest
```

veya:

```yaml
image: postgres
```

Cunku bunlar zamanla degisebilir. Bugun baska major surum, ileride baska major surum
gelebilir. Bu da "benim makinemde calisiyordu, degerlendirmede farkli davrandi" gibi
problemlere yol acabilir.

Daha iyi secimler:

```yaml
image: postgres:18-alpine
```

veya:

```yaml
image: postgres:17-alpine
```

Eger Inception yorumunu "son stable major surum" diye uygularsan `18-alpine` mantikli.
Eger "sondan bir onceki stable major surum" diye uygularsan `17-alpine` mantikli.

Mevcut `16-alpine` calisir ve desteklenen bir stable surumdur, ama 17 Agustos 2026
itibariyla "son" veya "sondan bir onceki" stable major surum degildir. Bu yuzden
daha temiz olmak icin `17-alpine` ya da `18-alpine` dusunulebilir.

Buradaki `alpine` kismini da dogru yazalim: `alphine` degil, `alpine`.

`alpine`, Alpine Linux tabanli daha kucuk Docker imaji demektir. PostgreSQL ayni
PostgreSQL'dir; sadece container icindeki Linux tabani daha minimaldir.

Kaynak notu:

- PostgreSQL resmi sitesinde 17 Agustos 2026 itibariyla son release listesi:
  `18.6`, `17.11`, `16.15`, `15.19`, `14.24`.
- PostgreSQL resmi versioning politikasina gore major surumler yaklasik 5 yil
  desteklenir.

### 2. Soru: localhost'ta port olarak 5432 secilmesinin ozel bir anlami var mi? Bir gelenek mi?

Evet, `5432` PostgreSQL icin standart/default porttur.

Bir veritabani server'i calistiginda disaridan baglanti alabilmek icin bir TCP portunda
dinler. PostgreSQL'in varsayilan portu:

```text
5432
```

Bu yuzden su komutta port yazmiyoruz:

```bash
psql -U ayhan -d piscineds -h localhost -W
```

Aslinda psql burada varsayilan olarak sunu varsayar:

```text
host: localhost
port: 5432
```

Eger PostgreSQL'i baska porttan acsaydik, mesela host tarafinda `5433` kullansaydik:

```yaml
ports:
  - "127.0.0.1:5433:5432"
```

o zaman subject'in verdigi komut tek basina yetmezdi. Portu ayrica belirtmek gerekirdi:

```bash
psql -U ayhan -d piscineds -h localhost -p 5433 -W
```

Ama subject su komutu istiyor:

```bash
psql -U your_login -d piscineds -h localhost -W
```

Bu komutta `-p` yok. Dolayisiyla evaluator varsayilan PostgreSQL portu olan `5432`
uzerinden baglanmayi bekler.

Bu yuzden Compose dosyasinda:

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

kullaniyoruz.

Bu mapping'in anlami:

```text
host localhost:5432 -> container icindeki postgres:5432
```

Yani evet, `5432` hem gelenek hem de PostgreSQL'in resmi varsayilan portudur. Bu proje
icin ayrica subject komutuyla uyumluluk anlamina gelir.

### 3. Soru: "piscineds_data volume'u -> container icindeki /var/lib/postgresql/data klasoru" bu yol container icindeki yol mu yoksa host bilgisayar icindeki yol mu? Volume demek dosyalari host bilgisayarin icinde bir yerde sakliyorum demek degil mi? Container'in icinde olsa yol container silinince gitmez mi?

Bu cok onemli bir ayrim. Su satira bakalim:

```yaml
volumes:
  - piscineds_data:/var/lib/postgresql/data
```

Burada iki taraf var:

```text
piscineds_data                 -> Docker named volume adi
/var/lib/postgresql/data       -> container icindeki mount edilen yol
```

Yani `/var/lib/postgresql/data` container icindeki yoldur.

Ama bu yolun icerigi container'in normal gecici filesystem'inde tutulmaz. Docker bu
yola `piscineds_data` adli volume'u baglar.

Mantik soyledir:

```text
Docker'in host uzerinde yonettigi volume
        |
        v
container icinde /var/lib/postgresql/data olarak gorunur
```

Yani sen container icinden baktiginda PostgreSQL verisi burada durur:

```text
/var/lib/postgresql/data
```

Ama fiziksel olarak bu veri Docker'in host bilgisayarda yonettigi volume alaninda
saklanir.

Linux'ta Docker volume verileri genelde Docker'in kendi veri dizini altinda tutulur.
Buna dogrudan elle mudahale etmek iyi pratik degildir. Docker'in kendisine sorarak
volume'un nerede oldugunu gorebilirsin:

```bash
docker volume ls
```

Belirli volume'u incelemek icin:

```bash
docker volume inspect piscineds_data
```

Compose proje adina gore volume ismi bazen tam olarak `piscineds_data` degil,
`ex00_piscineds_data` gibi olusabilir. Bunu `docker volume ls` ile gorursun.

#### Container silinirse veri gider mi?

Sadece container silinirse named volume kalir.

Ornek:

```bash
docker compose down
```

Bu container'i durdurur ve siler, ama volume'u silmez. Veritabani verisi kalir.

Sonra tekrar:

```bash
docker compose up -d
```

dersen PostgreSQL ayni volume'u kullanir ve onceki database verisini bulur.

Ama su komutu calistirirsan:

```bash
docker compose down -v
```

buradaki `-v`, volume'lari da sil demektir. Bu durumda database verisi gider.

#### Neden container icindeki yolu yaziyoruz?

Cunku PostgreSQL container icinde veriyi nereye yazacagini bilir:

```text
/var/lib/postgresql/data
```

Resmi PostgreSQL Docker imaji icin bu dizin database data directory olarak kullanilir.
Biz de Docker'a diyoruz ki:

```text
PostgreSQL bu dizine veri yazsin, ama bu dizinin arkasi kalici Docker volume olsun.
```

Yani senin sezgin dogru: Volume, veriyi host tarafinda kalici tutar. Sadece Compose
syntax'inda sag tarafta container icindeki mount noktasi yazildigi icin ilk bakista
"veri container icinde mi?" gibi gorunebilir.

Ozet:

```text
piscineds_data
  Docker'in hostta yonettigi kalici volume'dur.

/var/lib/postgresql/data
  Container icinde PostgreSQL'in veri klasoru olarak gordugu yoldur.

container silinirse
  volume kalir, veri gitmez.

docker compose down -v calistirilirsa
  volume da silinir, veri gider.
```

### 4. Soru: Healthcheck mantigini tam anlamadim: container calisinca her 10 saniyede bir database calisiyor mu diye kontrol mu edilecek yani? Bu kontrolu nasil yapiyor `"CMD-SHELL", "pg_isready -U ayhan -d piscineds"` komutunu detayli bir sekilde aciklar misin? Container unhealthy durumuna gelince ne oluyor peki, uyari falan mi cikiyor?

Evet, mantik genel olarak su:

```text
Container calisiyor mu?
```

sorusu ile:

```text
Container icindeki PostgreSQL gercekten baglanti kabul etmeye hazir mi?
```

sorusu ayni sey degildir.

Bir container `running` durumda olabilir ama PostgreSQL henuz acilis islemlerini
bitirmemis olabilir. Ornegin ilk kurulumda database dosyalari hazirlaniyor olabilir.
Bu sirada container calisiyor gorunur, ama psql ile baglanmaya calisirsan hata
alabilirsin.

Healthcheck bu farki anlamak icin vardir.

Compose dosyasindaki healthcheck:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U ayhan -d piscineds"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 10s
```

#### test

```yaml
test: ["CMD-SHELL", "pg_isready -U ayhan -d piscineds"]
```

Bu Docker'a sunu soyler:

```text
Container'in saglik durumunu anlamak icin container icinde bu komutu calistir.
```

`CMD-SHELL`, komutun container icindeki shell uzerinden calistirilacagini belirtir.
Yani Docker container icinde kabaca su komutu kosar:

```bash
pg_isready -U ayhan -d piscineds
```

#### pg_isready

`pg_isready`, PostgreSQL ile gelen bir yardimci programdir. Amaci database server'in
baglanti kabul etmeye hazir olup olmadigini kontrol etmektir.

Bu komut normal bir SQL sorgusu calistirmaz. Tablo okumaz, veri degistirmez. Sadece:

```text
PostgreSQL server cevap veriyor mu?
Bu kullanici/database bilgisiyle baglanti denenebilir mi?
Server hazir mi?
```

gibi bir hazirlik kontrolu yapar.

#### -U ayhan

```bash
-U ayhan
```

Kontrolu `ayhan` PostgreSQL kullanicisiyle yap demektir.

Bu, environment bolumundeki su ayarla uyumludur:

```yaml
POSTGRES_USER: ayhan
```

#### -d piscineds

```bash
-d piscineds
```

Kontrolu `piscineds` database'i icin yap demektir.

Bu da environment bolumundeki su ayarla uyumludur:

```yaml
POSTGRES_DB: piscineds
```

#### Neden sifre yazmiyoruz?

Healthcheck container icinde calisir. PostgreSQL Docker imaji icinde local kontrol icin
`pg_isready` genellikle server'in cevap verip vermedigini anlamaya yeterlidir.

Bu healthcheck'in amaci kullanici girisi yapip veri okumak degil, PostgreSQL surecinin
baglanti kabul etmeye hazir olup olmadigini anlamaktir.

#### interval

```yaml
interval: 10s
```

Docker bu kontrolu her 10 saniyede bir yapar.

Yani evet: container calisirken Docker belirli araliklarla "database hazir mi?" diye
kontrol eder.

#### timeout

```yaml
timeout: 5s
```

Healthcheck komutu 5 saniye icinde cevap vermezse o deneme basarisiz sayilir.

#### retries

```yaml
retries: 5
```

Arka arkaya 5 basarisiz denemeden sonra Docker container'i `unhealthy` olarak isaretler.

#### start_period

```yaml
start_period: 10s
```

Container ilk acilirken PostgreSQL'in hazirlanmasi icin 10 saniyelik tolerans verir.
Bu sure icindeki basarisizliklar hemen ciddi hata olarak sayilmaz.

#### Container unhealthy olunca ne olur?

Tek basina healthcheck container'i otomatik olarak durdurmaz veya yeniden baslatmaz.
Asil yaptigi sey container'in durumunu etiketlemektir.

Ornegin:

```bash
docker ps
```

ciktisinda su tarz bir durum gorebilirsin:

```text
healthy
```

veya:

```text
unhealthy
```

Daha detayli bakmak icin:

```bash
docker inspect piscineds_postgres
```

Healthcheck loglari ve son hata bilgileri burada gorulebilir.

Compose ile:

```bash
docker compose ps
```

veya eski Compose ile:

```bash
docker-compose ps
```

durum gorulebilir.

Peki neden faydali?

Tek container'li ex00'da healthcheck daha cok sana ve evaluator'a net sinyal verir:

```text
PostgreSQL gercekten hazir.
```

Ileride bir uygulama container'i database'e baglanacaksa healthcheck daha da onemli
hale gelir. Cunku diger servisler `service_healthy` kosuluyla database hazir olana kadar
bekletilebilir.

### 5. Soru: Bu `networks: - piscineds_network` kismi ileriki modullerde lazim olacak mi?

Ex00 icin kesin zorunlu degil. Tek container calistiriyorsan Docker Compose zaten
otomatik olarak default bir network olusturabilir.

Ama bu kisim kotu veya gereksiz bir hata degil. Daha duzenli bir Compose yapisi verir.

Su bolum:

```yaml
services:
  postgres:
    networks:
      - piscineds_network
```

PostgreSQL servisinin `piscineds_network` adli Docker agina baglanacagini soyler.

Alttaki bolum de bu agi tanimlar:

```yaml
networks:
  piscineds_network:
    driver: bridge
```

`bridge`, Docker'in ayni host icindeki container'lar icin kullandigi klasik network
tipidir.

#### Tek container varken ne ise yarar?

Tek container varken cok dramatik bir faydasi yoktur. Su an sadece daha acik ve kontrollu
bir yapi saglar.

#### Ileriki modullerde lazim olur mu?

Bu Data Science Piscine'in sonraki egzersizlerinde veritabanina baglanan baska araclar
veya scriptler kullanabilirsin. Eger bunlar host makineden calisiyorsa:

```text
localhost:5432
```

uzerinden baglanacaklari icin Docker network detayini bilmek zorunda degiller.

Ama ileride ayni Compose projesine ikinci bir container eklersen, mesela:

```text
pgadmin
dbeaver benzeri web arac
python script container'i
data import container'i
```

o zaman network daha anlamli hale gelir.

Ornegin ayni Docker network icindeki baska bir container PostgreSQL'e su host adiyla
baglanabilir:

```text
postgres
```

Cunku `postgres`, Compose servis adidir.

Host makineden baglanti:

```text
localhost:5432
```

Ayni Docker network icindeki baska container'dan baglanti:

```text
postgres:5432
```

Bu ayrim cok onemli:

```text
localhost
```

bir container icindeyken "kendi container'im" demektir. Host makine demek degildir.
Bu yuzden container'lar arasi iletisimde servis adi kullanilir.

#### Bu projede kalsin mi?

Bence kalsin. Sebepler:

- Subject'e aykiri degil.
- Tek container icin zararli degil.
- Inception tarzina daha yakin, acik bir Docker yapisi verir.
- Ileride ayni Compose dosyasina ek servis koyarsan hazir altyapi olur.

Ama bilmen gereken sey su:

```text
Ex00'u gecmek icin custom network sart degil.
```

Bu daha cok duzen ve ileride genisletilebilirlik icin eklenmis bir iyi pratiktir.
