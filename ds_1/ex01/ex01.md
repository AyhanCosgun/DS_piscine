## 1. Egzersizin Amacı ve Subject Analizi

Subject belgesinde (`ds_1.pdf`) Exercise 01 için şu bilgiler yer alır:

```text
Turn-in directory : ex01/
Files to turn in  : customers_table.*
Allowed functions : All

• You have to join all the data_202*_*** tables together in a table called "customers"
```

### Veri Ambarı (DWH) Bağlamında Anlamı
- `ds_0` modülünde ham CSV dosyalarını (`data_2022_oct`, `data_2022_nov`, `data_2022_dec`, `data_2023_jan`) veritabanına aktardık (**Staging / Raw Zone**).
- `ds_1/ex01` aşamasında, aylara bölünmüş bu parçalı tabloları tek bir merkezi tabloda (`customers`) topluyoruz (**Consolidation / Base Layer**).
- Tabloların kolonları (`event_time`, `event_type`, `product_id`, `price`, `user_id`, `user_session`) birbirinin tıpatıp aynısı olduğu için burada yapılması gereken işlem **Dikey Birleştirme (Vertical Concatenation)** yani **`UNION ALL`**'dur.

> [!NOTE]
> **Neden `UNION` Değil de `UNION ALL`?**  
> Düz `UNION`, birleştirme yaparken tüm satırları karşılaştırıp mükerrer (duplicate) olanları hash/sort ile elemeye çalışır. Bu işlem 16+ milyon satırda devasa RAM ve disk I/O tüketir ve gereksiz yere dakikalar sürer. Ayrıca **ex02** egzersizi bizden zaten özel kurallarla (1 saniyelik toleransla) duplicate temizliği isteyecektir. Dolayısıyla ex01'de doğrudan ve en hızlı olan **`UNION ALL`** kullanılmalıdır.

## 2. Soru 1: Tablo İsimlerini Teker Teker mi Yazmalıyız, Yoksa Döngü ile mi Dolaşmalıyız?

Bu soru, **Statik Kodlama (Hardcoded/Manual)** ile **Dinamik Kodlama (Metadata-driven/Dynamic)** arasındaki mimari tercihle ilgilidir.

```
┌───────────────────────────────────────┐   ┌────────────────────────────────────────┐
│     YAKLAŞIM 1: STATİK (MANUEL)       │   │      YAKLAŞIM 2: DİNAMİK (DÖNGÜ/REGEX) │
├───────────────────────────────────────┤   ├────────────────────────────────────────┤

│ SELECT * FROM data_2022_oct           │   │ data_202*_*** formatındaki tabloları   │
```

1. **Pratik ve Güvenli Tercih (Statik):**

## 3. Soru 2: Döngü Kurulacaksa SQL ile Yapılabilir mi, Yoksa Bash Script mi Lazım?

> [!IMPORTANT]
> **Kesin Cevap: Bash script'e KESİNLİKLE MECBUR DEĞİLSİNİZ!**  
> Bu işlem **saf SQL (`customers_table.sql`)** içinde, PostgreSQL'in kendi yetenekleriyle son derece şık bir şekilde yapılabilir.

### Neden Bash Yerine Saf SQL Tercih Edilmelidir?
1. **DWH ve Veritabanı Kültürü:** Veritabanı içinde doğrudan çözülebilecek tablo birleştirme işlerini harici bir işletim sistemi kabuğuna (Bash) ve harici proses çağrılarına (`psql` pipe zincirleri) devretmek mimari olarak tavsiye edilmez.
2. **Taşınabilirlik:** Saf bir `.sql` dosyası DBeaver, pgAdmin veya herhangi bir SQL istemcisinde tek bir tıkla doğrudan çalıştırılabilir; bash script ise sadece Linux/macOS terminal ortamına bağımlıdır.
3. **Turn-in Dosyası:** Subject `customers_table.*` istediği için `customers_table.sql` teslim etmek en standart yoldur.

---

### SQL ile Dinamik Çözümün Yolları:

#### A) En Şık Yol: `string_agg` + Dinamik Tek Seferde Çalıştırma (Döngüsüz Dinamik SQL)
PostgreSQL'de satır satır döngü kurmak yerine, veritabanı kataloğundaki tablo isimlerini `string_agg` ile tek bir sorgu metnine birleştirip `EXECUTE` etmek performans ve şıklık açısından en üst seviyedir:

```sql
DO $$
DECLARE
    v_sql TEXT;
BEGIN
    -- 1. Hedef tablo varsa kaldır (İdempotency)
    DROP TABLE IF EXISTS customers;

    -- 2. data_202*_*** formatındaki tüm tabloları tek bir UNION ALL sorgusu halinde birleştir
    SELECT 'CREATE TABLE customers AS ' || 
           string_agg('SELECT * FROM ' || quote_ident(tablename), ' UNION ALL ' ORDER BY tablename)
    INTO v_sql
    FROM pg_tables
    WHERE schemaname = 'public'
      AND tablename ~ '^data_202[0-9]_[a-z]{3}$';

    -- 3. Sorguyu çalıştır
    IF v_sql IS NOT NULL THEN
        RAISE NOTICE 'Çalıştırılan Sorgu: %', v_sql;
        EXECUTE v_sql;
        RAISE NOTICE 'customers tablosu başarıyla oluşturuldu.';
    ELSE
        RAISE EXCEPTION 'Hata: Kriterlere uygun "data_202*_***" tablosu bulunamadı!';
    END IF;
END $$;
```

---

#### B) Klasik Döngü Yolu: PL/pgSQL `FOR ... LOOP`
Döngü mantığıyla yapmak isterseniz PostgreSQL'in anonim kod bloklarında (`DO $$ ... $$`) döngü şu şekilde kurulur:

```sql
DO $$
DECLARE
    r RECORD;
    v_first BOOLEAN := TRUE;
BEGIN
    DROP TABLE IF EXISTS customers;

    FOR r IN (
        SELECT tablename 
        FROM pg_tables 
        WHERE schemaname = 'public' 
          AND tablename ~ '^data_202[0-9]_[a-z]{3}$'
        ORDER BY tablename
    ) LOOP
        IF v_first THEN
            EXECUTE format('CREATE TABLE customers AS SELECT * FROM %I', r.tablename);
            v_first := FALSE;
            RAISE NOTICE '% tablosu oluşturuldu ve ilk veri yüklendi.', r.tablename;
        ELSE
            EXECUTE format('INSERT INTO customers SELECT * FROM %I', r.tablename);
            RAISE NOTICE '% tablosundaki veriler eklendi.', r.tablename;
        END IF;
    END LOOP;

    IF v_first THEN
        RAISE EXCEPTION 'Hata: Birleştirilecek hiçbir tablo bulunamadı!';
    END IF;
END $$;
```

> [!TIP]
> **Yöntem A vs Yöntem B Karşılaştırması:**  
> Yöntem A (`string_agg` ile tek seferde `CREATE TABLE AS ... UNION ALL ...`) çok daha hızlıdır. Çünkü PostgreSQL verileri tek bir toplu işlem (bulk write) olarak diske yazar. Yöntem B'de ise her ay için ayrı ayrı `INSERT` çalıştırılır ve işlem daha uzun sürer (WAL ve kilit maliyeti).

## 4. Soru 3: Tabloların Varlığını Kontrol Etmek Gerekir mi? `\set ON_ERROR_STOP on` Yeterli mi?

### 1. `\set ON_ERROR_STOP on` Nedir ve Ne Yapar?
- Bu komut PostgreSQL sunucusunun değil, **`psql` komut satırı istemcisinin** bir ayarıdır.
- Normalde `psql`, bir SQL komutu hata verse bile (örneğin tablo bulunamadı) sonraki satırları körü körüne çalıştırmaya devam eder.
- `\set ON_ERROR_STOP on` dendiğinde ise, **herhangi bir hata alındığı anda psql betiği derhal durdurur**, sonraki hiçbir komutu çalıştırmaz ve işletim sistemine hata kodu (`exit code != 0`) döner.
- Bu ayar, yarım kalmış işlemlerin veya hatalı tabloların commit edilmesini engelleyen **en temel güvenlik mekanizmasıdır**.

---

### 2. `ON_ERROR_STOP` Varken Tablo Varlığını Kontrol Etmek Gerekir mi?

Cevap, **hangi yaklaşımı kullandığınıza göre değişir:**

#### Durum A: Statik Sorgu Kullanıyorsanız (Manuel İsimler)
```sql
CREATE TABLE customers AS
SELECT * FROM data_2022_oct
UNION ALL
SELECT * FROM data_2022_nov ...
```
- Eğer `data_2022_oct` tablosu veritabanında yoksa, PostgreSQL motoru doğrudan şu hatayı üretir:  
  `ERROR: relation "data_2022_oct" does not exist`
- `\set ON_ERROR_STOP on` devrede olduğu için script **anında durur**, `COMMIT`'e geçemez ve transaction geri alınır (`ROLLBACK`).
- **Sonuç:** Statik sorgularda **ekstra bir varlık kontrolüne gerek yoktur**, `ON_ERROR_STOP` işini kusursuz yapar!

#### Durum B: Dinamik Sorgu Kullanıyorsanız (`pg_tables` / Döngü)
- Eğer `pg_tables` kataloğunu sorguladığınızda kriterlere uyan hiçbir tablo yoksa, PostgreSQL **HATA VERMEZ**. Sadece `0 satır` (boş sonuç) döner!
- SQL için boş sonuç kümesi dönmesi bir hata değildir; dolayısıyla **`ON_ERROR_STOP` tetiklenmez!**
- Eğer siz kodunuzda kontrol yapmazsanız:
  - `v_sql` değişkeni `NULL` kalır.
  - Kod sessizce hiçbir şey yapmadan biter.
  - Terminalde hata görmezsiniz ama ortada `customers` tablosu da oluşmamış olur!
- **Sonuç:** Dinamik kod yazıyorsanız **kesinlikle tablo varlığını / sayısını kontrol etmeli** ve eğer tablo yoksa `RAISE EXCEPTION` ile açıkça bir hata fırlatmalısınız:
  ```sql
  IF v_table_count = 0 OR v_sql IS NULL THEN
      RAISE EXCEPTION 'HATA: "data_202*_***" desenine uyan hiçbir tablo bulunamadı!';
  END IF;
  ```

#### Durum C: `DROP TABLE IF EXISTS customers;` Kontrolü (İdempotency)
- Betiği 2. veya 3. kez çalıştırdığınızda (veya test ederken), `customers` tablosu zaten var olacağı için `CREATE TABLE customers` hata verir.
- Bu nedenle betiğin başına `DROP TABLE IF EXISTS customers;` eklemek şarttır. `IF EXISTS` eklemezseniz ilk çalıştırmada tablo henüz yokken `DROP TABLE` hata verir ve `ON_ERROR_STOP` scripti hemen durdurur!

### Seçenek 2: Dinamik Çözüm (Şık ve Profesyonel: Regex + Katalog Taraması)

Eğer evaluatör'e SQL yeteneklerinizi sergilemek ve `data_202*_***` kalıbını dinamik karşılamak isterseniz:

```sql
\echo '================================================================================'
\echo 'Processing: customers_table.sql (Dynamic Metadata Approach)'
\echo '================================================================================'

\set ON_ERROR_STOP on

BEGIN;

DROP TABLE IF EXISTS customers;

DO $$
DECLARE
    v_sql TEXT;
    v_table_count INT;
BEGIN
    -- 1. Kriterlere uyan kaç tablo olduğunu say ve dinamik sorguyu oluştur
    SELECT count(*), 
           'CREATE TABLE customers AS ' || 
           string_agg('SELECT * FROM ' || quote_ident(tablename), ' UNION ALL ' ORDER BY tablename)
    INTO v_table_count, v_sql
    FROM pg_tables
    WHERE schemaname = 'public'
      AND tablename ~ '^data_202[0-9]_[a-z]{3}$';

    -- 2. Tablo varlık kontrolü (Tablo yoksa hata fırlat ki ON_ERROR_STOP devreye girsin)
    IF v_table_count = 0 OR v_sql IS NULL THEN
        RAISE EXCEPTION 'HATA: "data_202*_***" desenine uyan hiçbir tablo bulunamadı!';
    END IF;

    RAISE NOTICE 'Toplam % adet tablo bulundu. Birleştirme işlemi başlatılıyor...', v_table_count;

    -- 3. Dinamik sorguyu tek seferde yürüt
    EXECUTE v_sql;

    RAISE NOTICE 'customers tablosu başarıyla oluşturuldu.';
END $$;

\echo '================================================================================'
COMMIT;
```

## 8. Dinamik SQL ve PL/pgSQL Mantığı: 7 Soruda Adım Adım Rehber

Bu bölüm, dinamik çözümde kullanılan `DO $$ ... END $$`, `DECLARE`, `string_agg`, `quote_ident`, `||`, `INTO`, `RAISE` ve `EXECUTE` kavramlarını sıfırdan, en temel mantığıyla ve küçük örnek tablolarla kavramanız için hazırlanmıştır.

---

### 8.1. `DO $$ ... END $$` Yapısı Nedir ve Hangi Durumlarda Kullanılır?

#### Standart SQL'in Sınırları
Standart SQL **bildirimseldir (declarative)**. Yani veritabanına *"bana şu veriyi getir (`SELECT`)"* veya *"şu satırı ekle (`INSERT`)"* dersiniz. Ancak standart SQL içinde şunları **yapamazsınız**:
- Değişken tanımlamak,
- `IF / ELSE` mantıksal dallanması kurmak,
- `FOR / WHILE` döngüsü çalıştırmak,
- Çalışma anında üretilen bir metni SQL komutu olarak yürütmek (Dinamik SQL).

#### PL/pgSQL ve `DO` Bloğunun Doğuşu
PostgreSQL, SQL'e bu programlama yeteneklerini kazandırmak için **PL/pgSQL (Procedural Language for PostgreSQL)** dilini geliştirmiştir.

Eski yöntemlerde bu mantığı çalıştırmak için önce `CREATE FUNCTION my_func() ...` diyerek veritabanına kalıcı bir fonksiyon kaydetmeniz, sonra da onu çalıştırmanız gerekirdi. Fakat sadece o an bir kerelik çalışacak bir işlem için veritabanına kalıcı fonksiyon bırakmak veritabanını kirletir.

İşte **`DO $$ ... END $$;`**, **Anonim (İsimsiz) Kod Bloğu** demektir:
- Tıpkı Python'daki bir `lambda` fonksiyonu veya terminaldeki tek satırlık bir script gibidir.
- Bellekte geçici olarak çalışır, işini bitirir ve veritabanında hiçbir kalıntı bırakmadan yok olur.

#### Neden `$$` (Dolar Tırnağı - Dollar Quoting)?
SQL'de metinler tek tırnak (`'...'`) içine yazılır. Eğer onlarca satırlık PL/pgSQL kodunu tek tırnak içine alsaydık, içeride kullanacağımız her tek tırnak için kaçış karakteri (`''`) yazmak zorunda kalırdık (tırnak karmaşası / quote hell).  
`$$` işareti, PostgreSQL'e şunu söyler: *"Bu iki `$$` arasındaki hiçbir şeye dokunma; içinde ne kadar tırnak, noktalı virgül veya yeni satır olursa olsun hepsini tek bir kod bloğu olarak kabul et."*

#### Basit Tablo Örneği:
Elimizde bir `ogrenciler` tablosu olsun:

| id | ad | notu |
| :---: | :---: | :---: |
| 1 | Ahmet | 40 |
| 2 | Zeynep | 45 |
| 3 | Can | 50 |

**Senaryo:** Sınıfın ortalaması 50'nin altındaysa herkese 10 puan ekleyelim, değilse eklemeyelim.  
Standart SQL ile bu kontrolü tek bir komutla yapamazsınız; `DO` bloğu ile:

```sql
DO $$
DECLARE
    v_ortalama NUMERIC;
BEGIN
    -- Ortalamayı değişkene al
    SELECT AVG(notu) INTO v_ortalama FROM ogrenciler;

    -- Şarta göre karar ver
    IF v_ortalama < 50 THEN
        UPDATE ogrenciler SET notu = notu + 10;
        RAISE NOTICE 'Ortalama düşük (% idi). Herkese 10 puan eklendi!', v_ortalama;
    ELSE
        RAISE NOTICE 'Ortalama yeterli (%). Notlara dokunulmadı.', v_ortalama;
    END IF;
END $$;
```

---

### 8.2. `DECLARE` ve `v_sql` Değişkeni: SQL Ortamında Değişken Tanımlama

#### `DECLARE` Bloğu ve Veri Tipleri
- `DECLARE`, bloğun içinde kullanılacak tüm değişkenlerin hafızada yer ayrıldığı bölümdür.
- **Evet, PostgreSQL'deki TÜM SQL veri tipleri burada geçerlidir!**
  - Temel Tipler: `INTEGER`, `BIGINT`, `NUMERIC`, `TEXT`, `VARCHAR`, `BOOLEAN`, `DATE`, `TIMESTAMPTZ`
  - Gelişmiş Tipler: Diziler (`TEXT[]`), Tablo Satır Tipi (`customers%ROWTYPE`), Genel Kayıt Tipi (`RECORD`)

#### `v_sql` Kodu Nasıl Toplar?
- SQL motoru için bir SQL komutu aslında özünde **düz bir metinden (string)** ibarettir.
- `v_sql TEXT;` tanımı: *"Hafızada `v_sql` adında, sınırsız uzunlukta metin tutabilen bir değişken aç"* demektir.
- Biz bu değişkeni bir **"metin kumbarası"** gibi kullanırız. Önce `'CREATE TABLE customers AS '` yazarız, sonra arkasına tablo isimlerini ekleriz, en sonunda da bu metni çalıştırırız.

### 8.3. Neden `'CREATE TABLE customers AS '` Tek Tırnak İçinde ve `||` Ne İşe Yarar?

#### Neden Tek Tırnak?
**Çünkü onu o anda çalıştırmak istemiyoruz, sadece bir metin parçası olarak birleştirmek istiyoruz!**
- Eğer tek tırnak koymasaydınız:
  `SELECT CREATE TABLE customers AS ...`
  PostgreSQL hemen `Syntax Error` verirdi; çünkü `SELECT` ifadesinden sonra bir SQL komutu yazılamaz.
- Tek tırnak koyarak veritabanına deriz ki: *"Bu henüz bir komut değil, bu sıradan bir yazı! Sen bunu sadece bir metin olarak al ve değişkenin içine koy."*
- Biz burada **Metaprogramming (Kod Üreten Kod / Dinamik SQL)** yapıyoruz.

#### `||` Bağlacı Nedir?
- SQL standardında ve PostgreSQL'de `||` operatörü **Metin Birleştirme (String Concatenation)** aracıdır.
- Python veya JavaScript'teki string toplama (`+`) işleminin birebir aynısıdır:
  ```sql
  'Merhaba ' || 'Dünya'  -- Sonuç: 'Merhaba Dünya'
  ```
- Bizim kodumuzda:
  ```sql
  'CREATE TABLE customers AS ' || 'SELECT * FROM data_2022_oct ...'
  ```
  işlemi iki metni uç uca ekleyerek tek bir uzun SQL sorgu metnine dönüştürür.

### 8.4. `string_agg` ve `quote_ident` Fonksiyonları Nasıl Çalışır?

#### `string_agg(ifade, ayraç)` Fonksiyonu
- Tıpkı `SUM(fiyat)` fonksiyonunun sütundaki tüm sayıları toplayıp tek bir sayı üretmesi gibi; `string_agg(metin, ayraç)` fonksiyonu da birden fazla satırdaki metinleri aralarına belirttiğiniz ayracı koyarak **tek bir satırda ve tek bir metinde** birleştirir.

**Küçük Tablo Örneği:**  
Elimizde bir `sepet` tablosu olsun:

| urun |
| :--- |
| Elma |
| Armut |
| Muz |

```sql
SELECT string_agg(urun, ' - ') FROM sepet;
```
**Dönen Sonuç:** `'Elma - Armut - Muz'`

#### Kodumuzda `string_agg` Nasıl Çalışıyor?
`pg_tables` kataloğundan eşleşen tablo isimlerimiz şunlardır:
1. `data_2022_oct`
2. `data_2022_nov`
3. `data_2022_dec`
4. `data_2023_jan`

Biz kodda şunu yazıyoruz:
```sql
string_agg('SELECT * FROM ' || quote_ident(tablename), ' UNION ALL ')
```
Her satır için `'SELECT * FROM ' || tablename` ifadesi hesaplanır:
- 1. satır: `SELECT * FROM "data_2022_oct"`
- 2. satır: `SELECT * FROM "data_2022_nov"`
- 3. satır: `SELECT * FROM "data_2022_dec"`
- 4. satır: `SELECT * FROM "data_2023_jan"`

`string_agg` bu 4 satırı alır ve aralarına `' UNION ALL '` yapıştırarak tek bir metne dönüştürür:
`'SELECT * FROM "data_2022_oct" UNION ALL SELECT * FROM "data_2022_nov" UNION ALL SELECT * FROM "data_2022_dec" UNION ALL SELECT * FROM "data_2023_jan"'`

#### `quote_ident(isim)` Fonksiyonu
- Veritabanı nesne isimlerini (tablo veya sütun adı) güvenli bir şekilde **çift tırnak** içine alır (`"..."`).
- **Neden Önemlidir?**
  1. **Özel Karakter Koruması:** Eğer bir tablonun adı tire (`data-2022`) veya boşluk içeriyorsa, çift tırnak olmadan SQL hata verir.
  2. **Rezerve Kelime Koruması:** Eğer bir tablonun adı `user`, `order`, `table` gibi SQL'in kendi komut kelimelerinden biriyse, çift tırnaksız kullanım çöker.
  3. **SQL Injection Güvenliği:** Dinamik SQL oluştururken dışarıdan gelebilecek zararlı tablo isimlerini etkisiz hale getirir.

### 8.5. `INTO` Komutu Değişkenlere Değer Atamak İçin midir?

**Evet, kesinlikle öyledir!**

- Düz SQL'de `SELECT 5 + 5;` derseniz sonuç ekrana (terminal penceresine) basılır.
- Ancak bir programlama bloğu içinde çalışırken amacımız sonucu ekrana basmak değil, bir değişkenin içine kaydetmektir.
- PL/pgSQL'de `SELECT ... INTO degisken` sözdizimi kullanılır:
  ```sql
  SELECT count(*) INTO v_tablo_sayisi FROM pg_tables WHERE ...;
  ```
  Burada `count(*)` hesaplanır ve değeri doğrudan `v_tablo_sayisi` isimli tamsayı değişkeninin içine yazılır. Artık sonraki satırlarda bu değişkenle `IF v_tablo_sayisi = 0 THEN ...` kontrolü yapabilirsiniz.

### 8.6. `RAISE NOTICE` ve `RAISE EXCEPTION` da `DO $$ ... END $$` Kalıbının Bir Parçası mıdır?

**Evet! Bunlar PL/pgSQL dilinin yerleşik mesaj ve istisna (exception) mekanizmalarıdır.** (Düz SQL sorgularında tek başına kullanılamazlar).

```
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│            RAISE NOTICE              │     │           RAISE EXCEPTION            │
├──────────────────────────────────────┤     ├──────────────────────────────────────┤
│ • Bilgilendirme amaçlıdır.           │     │ • Hata fırlatma amaçlıdır.           │
│ • Konsola mesaj yazar.               │     │ • Çalışmayı ANINDA DURDURUR!         │
│ • Program çalışmaya devam eder.      │     │ • Transaction iptal olur (ROLLBACK). │
│ • Python'daki print() gibidir.       │     │ • Python'daki raise Exception() dır. │
└──────────────────────────────────────┘     └──────────────────────────────────────┘
```

- **`RAISE NOTICE` Örneği:**
  ```sql
  RAISE NOTICE 'Bulunan tablo sayısı: %', v_table_count;
  ```
  Buradaki `%` işareti, tıpkı C dilindeki `printf` veya Python format string (`f"..."`) gibi değişkenin değerini yerine koyar.

- **`RAISE EXCEPTION` Örneği:**
  ```sql
  RAISE EXCEPTION 'HATA: Tablo bulunamadı!';
  ```
  Bu satır çalıştığı an PostgreSQL bir `ERROR` fırlatır, transaction iptal edilir ve scriptin başında koyduğumuz `\set ON_ERROR_STOP on` bu hatayı yakalayıp scripti güvenli şekilde sonlandırır.

### 8.7. `EXECUTE`: Tetiğin Çekildiği An ve Scriptin Adım Adım Akışı

**Harika bir tespit: Asıl çalıştırma kesinlikle `EXECUTE` satırında başlar!**

`EXECUTE` satırına gelene kadar veritabanında **hiçbir tablo oluşturulmaz ve tek bir satır veri dahi taşınmaz.** O ana kadarki bütün adımlar bir mimarın inşaat planını kağıda çizmesi gibidir. `EXECUTE v_sql;` ise o planı inşaat ustasına verip *"Binayı inşa et!"* dediğimiz andır.

#### Adım Adım Akış Şeması (Basit 2 Tablo Örneğiyle):

Diyelim veritabanımızda sadece `data_2022_oct` ve `data_2022_nov` tabloları var.

```text
[ BAŞLA: DO $$ ]
       │
       ▼
[ ADIM 1: DECLARE ]
Hafızada boş değişkenler tanımlanır:
v_table_count = NULL
v_sql = NULL
       │
       ▼
[ ADIM 2: SELECT ... INTO v_table_count, v_sql ]
pg_tables kataloğu taranır:
1) v_table_count = 2 olarak hesaplanır.
2) string_agg çalışır:
   'SELECT * FROM "data_2022_oct"' ve 'SELECT * FROM "data_2022_nov"' metinleri aralarına ' UNION ALL ' koyularak birleştirilir.
3) Başlık eklenir:
   v_sql = 'CREATE TABLE customers AS SELECT * FROM "data_2022_oct" UNION ALL SELECT * FROM "data_2022_nov"'
       │
       ▼
[ ADIM 3: GÜVENLİK KONTROLÜ (IF ... THEN) ]
v_table_count = 0 mı? Hayır (2).
v_sql boş mu? Hayır.
(Demek ki tablolar bulundu, RAISE EXCEPTION atlamadan geçilir).
       │
       ▼
[ ADIM 4: EXECUTE v_sql ] <====== TETİK BURADA ÇEKİLİR!
PostgreSQL motoru v_sql'in içindeki metni alır.
Sanki klavyeden tek tek siz yazmışsınız gibi:
"CREATE TABLE customers AS SELECT * FROM data_2022_oct UNION ALL SELECT * FROM data_2022_nov"
komutunu derler, çalıştırır ve "customers" tablosunu fiziksel olarak oluşturup doldurur!
       │
       ▼
[ ADIM 5: RAISE NOTICE ]
Terminale yeşil/bilgi mesajı basılır:
"NOTICE: customers tablosu başarıyla oluşturuldu."
       │
       ▼
[ BİTİŞ: END $$; ve COMMIT ]
Geçici kod bloğu bellekten silinir. COMMIT ile tüm değişiklikler kalıcı olur.
```

## 9. Commit Öncesi Kayıt Sayısı Kontrolü ve Rollback

Dinamik olarak oluşturulan `customers` tablosunun doğruluğunu kontrol etmek
için `COMMIT` işleminden hemen önce kaynak tabloların toplam satır sayısı ile
`customers` tablosunun satır sayısı karşılaştırılabilir.

Kontrol başarısız olursa `RAISE EXCEPTION` hata üretir. Hata transaction
içerisinde oluştuğu için transaction başarısız duruma geçer; ayrıca dosyanın
başındaki `\set ON_ERROR_STOP on` nedeniyle `psql` scripti durdurur ve
`COMMIT` çalışmaz. Böylece transaction rollback edilir.

Dinamik çözümdeki mevcut `COMMIT;` satırından hemen önce aşağıdaki bölüm
eklenmelidir:

```sql
\echo '--------------------------------------------------------------------------------'
\echo 'Beklenen ve oluşan kayıt sayıları kontrol ediliyor...'

DO $$
DECLARE
  v_beklenen_toplam BIGINT;
  v_olusan_toplam BIGINT;
BEGIN
  RAISE NOTICE 'Beklenen kayıt sayısı hesaplanıyor...';

  SELECT
    (SELECT count(*) FROM data_2022_oct) +
    (SELECT count(*) FROM data_2022_nov) +
    (SELECT count(*) FROM data_2022_dec) +
    (SELECT count(*) FROM data_2023_jan)
  INTO v_beklenen_toplam;

  RAISE NOTICE 'customers tablosundaki kayıt sayısı hesaplanıyor...';

  SELECT count(*)
  INTO v_olusan_toplam
  FROM customers;

  RAISE NOTICE 'Beklenen toplam: %, oluşan toplam: %',
    v_beklenen_toplam,
    v_olusan_toplam;

  IF v_beklenen_toplam <> v_olusan_toplam THEN
    RAISE EXCEPTION
      'Kayıt sayısı uyuşmuyor! Beklenen: %, Oluşan: %',
      v_beklenen_toplam,
      v_olusan_toplam;
  END IF;

  RAISE NOTICE 'Kontrol başarılı: kayıt sayıları eşleşiyor.';
END $$;

\echo 'Kontrol başarılı, transaction commit ediliyor.'
```

Bu kontrol başarılı olduktan sonra mevcut `COMMIT;` satırı çalışır. Böylece
`customers` tablosu yalnızca beklenen toplam kayıt sayısını içeriyorsa kalıcı
hale getirilir.
